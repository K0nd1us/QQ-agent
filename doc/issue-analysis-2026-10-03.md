# QQ-Agent 三项问题核查报告

核查版本：工作树 `main-8d70488f`（HEAD = `11577ba v0.4 Preview`）
核查时间：2026-10-03

## 结论速览

| # | 用户描述 | 是否成立 | 一句话结论 |
|---|---|---|---|
| 1 | 缓存命中率低，系统时间放开头拉低命中率 | **部分成立** | 用户描述的那个具体机制在当前版本**已不存在**（时间在末尾）；但确实存在其它几个真实的"前缀缓存杀手" |

## 问题一：缓存命中率

### 用户描述的具体机制：已修复

【当前时间】确实被刻意放在**用户提示的最末尾**，且系统提示里没有任何时间：

- `src/prompt.js:885-887`
  ```js
  // 【当前时间】放最末：精确到秒、每次必变 —— 放前面会把整个用户提示的
  // 缓存前缀打断（模型知道"现在"的时效性靠这里，内容本身不受段落顺序影响）。
  parts.push(`【当前时间】${formatFullTime(now)}`);
  ```
- 段落排序整体按"变化频率"设计：`角色设定 → 可用表情包 → 引导说明 → 记忆 → 已读信息 → 新已读信息 → 未读信息 → 新加入成员 → 当前时间`（`prompt.js:776-887`）。
- 系统提示 `buildSystemPrompt()`（`prompt.js:212-284`）全文不含时间；全文 grep 只有 `prompt.js:714` 一处 `Date.now()`。

> 所以"把时间放开头"这条，在当前代码里**不成立**。若用户是在成品安装包装上观察到的，那很可能是从更早提交构建的包。

### 但"缓存命中率低"是真的，真实原因如下

**(a) 【记忆】段的成员顺序不稳定 —— 影响最大**

- `src/memory.js:264`：`members()` 按 `updatedAt` **降序**排序。
- `src/memory.js:455-470`：`formatForPrompt()` 直接沿用这个顺序（`all.slice`/`filter` 不重排）。
- 任何一次 `remember_member` 写入都会更新该成员的 `updatedAt`（`memory.js:216`）→ 该成员跳到列表最前 → **【记忆】段字节整体变化**。
- 而【记忆】排在【已读信息】**之前**（`prompt.js:825` 早于 `prompt.js:828`），它一变，后面整段已读信息（通常 prompt 的 token 大头）全部 cache miss。
- 这直接违背锚点设计的核心前提——`prompt.js:784-786` 注释写的"记忆段……跨轮稳定的字节前缀"。**锚点把"已读信息"稳住了，却被"记忆"的排序捅穿。**

**(b) 锚点续用窗口太窄**

- 续用条件之一是"锚点之后的已读条数 ≤ `maxExtraRead`"（默认 **5**，`src/config.js:275-278`；判定在 `prompt.js:677`）。
- 群里稍热闹，两次触发间就新增 >5 条 → 立即 `reset`（`prompt.js:677` 走 `freshAnchor()`）。
- reset 后【已读信息】退回**滑动窗口**：`buildPastState()` 取 `store.recent(...).slice(-maxLimit)`（`prompt.js:523/539`），窗口每次整体前移 → 前缀在已读信息处断裂。
- 结论：**只有连续、密集触发才可能吃到锚点红利；日常"新对话"几乎必然 reset**。

**(c) 【可用表情包】段会自己变**

- 选中集合的排序键包含 `useCount`（`src/stickers.js:152-157`）：机器人每发一次表情，该表情 `useCount+1`，可能挤进/挤出选中列表 → 该段字节变化（且它比【记忆】更靠前）。
- 另有 60 分钟轮换（`src/stickers.js:159-178`，`round = floor(now/period)`）——即使不发话，每小时也会刷新一次该段。

**(d) 系统提示本身也会变**

- 参与度档位写进系统提示：`speakOrNot(cfg.participation)`（`prompt.js:258`）。会话级人设（`personaByChat`）参与度不同 → **系统提示不同**（`orchestrator.js:816-822`）。
- owner-identity 命中时会往系统提示插 `extraSections`（`orchestrator.js:819-821`）→ 主人说话/不说话两种情况下系统提示字节不同 → **连系统提示前缀都全废**。

**(e) 没有显式 cache 断点**

- 请求体只有 `model/messages/stream/tools/tool_choice/max_tokens/temperature`（`src/llm.js:300-315`），没有 `cache_control`。
- 对 DeepSeek / Qwen / GLM 这类"自动前缀缓存"没问题；对**需要显式 `cache_control` 的网关（如 Anthropic 直连/部分中转）等于完全没开缓存**。

**(f) 指标口径本身会显得"低"**

- 命中率 = `cachedTokens / promptTokens`（`src/llm.js:624-628`）。
- `historyCount` 固定 80（`src/config.js:266`），单次 prompt 里【已读信息】占大头；即便系统提示全命中，比率也上不去。

**建议（按性价比排序）**
1. 【记忆】段改用**稳定排序**：按 `userId` 字典序（或固定成员集顺序）输出，与 `updatedAt` 解耦，只让新印象追加到该成员行尾。
2. 让【记忆】/【可用表情包】**不参与**"已读信息之前的前缀"——把二者移到【未读信息】之后（易变区），保证"系统提示 + 角色设定 + 已读信息"成为长稳前缀。
3. 提高 `maxExtraRead`（如 15~20）或改成"按 token 预算"而非固定条数，让锚点在正常群速下也能续上。
4. 表情选中列表去掉 `useCount` 作为排序键，或把 `useCount` 改为低频快照。
5. 需要显式缓存的网关补 `cache_control` 断点（系统提示末尾 + 已读信息末尾）。

## 问题二：思考未落盘（成立，且是设计层缺口）

### 证据链

1. **模型正文/思考不进任何长期存储**
   - `src/orchestrator.js:1022-1031`：把 `msg.content` 作为 `assistant` 条目 push 进 `session.messages` —— 只活在**本次会话记录**里。
   - 会话的定位本身就是"用完即弃"：`src/prompt.js:5-8` 注释 + README「会话结束即弃置，LLM 层面零历史」。
   - 会话文件虽写盘（`src/sessions.js:343-366` `finish()` → `#persist`），但按 `keepFiles` 会被清理，且**没有任何代码把它回灌进下一次提示词**。
2. **原生思考（reasoning）也没落盘**
   - `src/llm.js:513-516` + `src/thinking.js:283-312`：`reasoning_content` 只被提取到 `result.reasoning`，随后无持久化。
3. **记忆模块的 schema 只允许"对群友的印象"**
   - 工具层：`src/tools.js:652-672`，`category` 的 `enum` **只有** `['memberImpression']`。
   - 存储层：`src/memory.js:222-229`，`append()` 里 `if (category !== 'memberImpression') return null;`。
   - 数据结构：`data/memory/<会话>/<QQ>.json`，一个**群友**一份（`memory.js:1-5`）——根本没有"我自己"的位置。
4. **最直接的证据：旧能力被显式删除**
   - `src/memory.js:124`：`// 旧的 activeTopic/pendingThought 直接丢弃（本版只保留群友印象）`。
   - 也就是说，历史上曾经有过"待办思考"的落盘点，本版被砍掉了。

### 为什么"海龟汤"必丢

每轮新开会话时，能跨轮带过来的只有两样：
- 【已读信息】= 存档里**实际发出去的**消息（`buildPastState`，`prompt.js:518-544`，只含 `self`/群友已读消息）；
- 【记忆】= **对别人**的印象。

海龟汤的答案/出题人视角属于"机器人私有状态"：它没发到群里，就不在存档里；它也不是"对某人的印象"，就进不了记忆。于是下一轮机器人完全不记得自己是出题人、答案是啥 —— 只能靠 80 条历史里别人零星的发言反推，信息量大幅塌缩。

### 建议

1. 新增一类**自身状态记忆**（如 `selfNotes` / `sessionState` / `secret`）：`memory.js` 放开 category，落 `_self.json`，在提示词里单独一段（建议放易变区）注入。
2. 给模型配一个 `remember_self` / `set_secret` / `update_self_note` 工具（现有 `remember_member` 的姊妹工具）。
3. 或者：把模型私有推理以**隐藏行**写进存档（标记 `hidden: true`，不发给 QQ，但会进下一轮【已读信息】）——改动最小，能立刻救活所有"扮演/游戏/长任务"场景。
4. 原生 `reasoning_content` 也顺带落一份（调试+复盘都能用）。

## 问题三：三档低概率触发导致"突然不回复"（成立）

### 机制

1. **3 档 = 与内容完全无关的纯概率门**
   - `src/prompt.js:482-483`：`rollValue = Math.random()*100`；`randomHit = rollValue < randomPercent`。
   - `src/prompt.js:504-508`：`if (tier >= 3 && randomHit) return { tier:3, shouldRespond:true }`。
   - 骰子只看随机数，**完全不看**"这条消息是不是在接你的话"。
2. **没有"回复我"特判**
   - 触发只认四种信号：被 @（`atMe`，`prompt.js:470-473` / `app.js:886-892`）、关键词（`prompt.js:501-502`）、随机（`504-508`）、拍一拍我（`487-490`）。
   - 引用/回复机器人的消息**不算触发**。`triggerLabels()` 里那个 `'引用'` 标签只是给人/模型看的描述（`prompt.js:564`），**不参与判定**。
   - 顺带说明：引用关系其实*是*能拿到的——`onebot.js:458-476` 会把 `reply` 段渲染成 `[引用 名字(QQ:xxx)：原文]` 进 `text`，所以"回我"是可检测的，只是判定层没用它。
3. **不触发 = 一次定生死**
   - `src/orchestrator.js:191-201`：判定不通过就**当场标已读**，消息沉入历史，不建会话、不再补判。
   - 除非之后有人 @，否则这条"接你话"的消息永远不会再被处理 → 群里表现就是**机器人忽然不回、话题断掉**。
4. **唯一的补偿默认关闭，且门槛高**
   - `src/config.js:237-240`：`chatActive.enabled = false`（默认关）。
   - 即便开启，也要**模型主动在 finish 时带回 `activeTopic`** 才进入活跃期（`orchestrator.js:1200-1211`），且 `activeTopics` 是内存态（`orchestrator.js:60`），重启即丢。

### 需要承认的部分

"不每条都回、按概率插话"是这个项目的**成本控制核心设计**（README 技术架构第 2-4 条），本身不是 bug。真正的问题在于：3 档把"内容相关度"这个最重要的信号权重设成了 0——**越是"顺着你说"的接话，越容易被随机数卡住**，而这恰恰是最该接的一类。

### 建议

1. **"回复我"升格为触发**：文本匹配 `[引用 <机器人昵称>(QQ:<selfId>)：` 即视为召唤（等价被 @）。
2. **连贯窗口**：机器人自己发完言后的 N 秒（如 90s）内，该会话视为高优先级，直接必响应（可复用现有 `activeTopics` 结构，只是自动进入而非靠模型触发）。
3. **3 档骰子加偏置**：当最新消息是对机器人的直接回应时，把生效概率抬到一个下限（如 ≥60%），而非纯线性。
4. **未触发别立刻判死**：给一个短 TTL（5~10s）的"再判一次"机会——期间若来了上下文相关的消息，合并重判/重掷，而不是直接标已读。
