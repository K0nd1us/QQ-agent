## 一、问题①：缓存命中率

### 根因回顾

稳定前缀链本应是：
```
系统提示 → 【角色设定】 → 【可用表情包】 → 【引导说明】 → 【记忆】 → 【已读信息】
```
但其中 **【可用表情包】和【记忆】两段字节会自己变**，而它们都排在【已读信息】**之前**。
前缀缓存只要遇到第一个不同字节就整段失效 —— 于是这两段一抖，后面最大的一块（已读信息，通常占 token 大头）全部 miss。

（时间位置已没问题：`prompt.js:885-887` 在最末；系统提示里无时间。）

### 改动清单

**A1　【可用表情包】段稳定化**（必做，最靠前）
- 文件：`src/stickers.js:148-190`
- 现状：选中集合的排序键含 `useCount`（`152-157`）；另有 60 分钟轮换（`159-178`）。
- 改法：排序键去掉 `useCount`（改为按 `id` 字典序稳定排）；`rotatePeriodMin` 默认改为 `0`（关闭）或提到 24h。
- 代价：常用表情不再自动上浮。可另加"常用区"由用户手动置顶，且不计入提示词段。
- 测试：`test/sticker-context.mjs:54-75` 目前只断言"计数变化不改文本"，但用的数据**相对顺序不变**，覆盖不到重排场景 —— 需补一条"计数重排后文本仍不变"的断言。

**A2　【记忆】段字节稳定化**（核心，二选一）
- 文件：`src/memory.js:251-266`（`members()` 按 `updatedAt` **降序**）、`455-470`（`formatForPrompt()` 直接沿用该顺序）
- 现状问题：任何一次 `remember_member` 都会更新该成员 `updatedAt` → 该成员跳到列表最前 → 【记忆】整段字节变 → 其后全部失效。
- **方案 A2-①（推荐先做，改动小）**：`formatForPrompt` 内部独立排序 —— 按 `userId` 升序输出成员；成员印象按 `createdAt` 升序。
  - 局限：新写入一条印象仍会改变该成员块 → 仍会打断其后字节（只是断裂点从"最顶"下移到该成员位置）。
  - 也就是说 A2-① 只解决"排序抖动"，解决不了"内容增长"。
- **方案 A2-②（彻底）**：注入**冻结快照** —— 【记忆】段只输出一份编译版文本，仅在整合（consolidation）或手动"更新记忆"后重算，不随单条印象变化。
  - 复用现成机制：`memory.js:472-569` 已有 consolidation / `replaceConsolidated` / `markConsolidated`。
  - 需新增字段（如 `compiledText` / `compiledAt`）与失效时机。
  - 代价：新写入的印象要等下次整合才进提示词（可用"超阈值自动整合"兜住时效）。

**A3　备选：把【记忆】挪到易变区**（若 A2 判定太复杂）
- 文件：`src/prompt.js:787-889`
- 新顺序：`角色设定 → 引导说明 → 已读信息 → 新已读信息 → 未读信息 → 记忆 → 新加入成员 → 当前时间`
- 连带影响（重要）：
  - 锚点语义要改：`resolvePromptAnchor` 的 `memberIds` / `hasNewMember→reset`（`prompt.js:655-658`）失去存在意义，可简化；
  - 锚点稳定前缀缩为"系统 + 角色设定 + 引导说明 + 已读信息"；
  - **测试必改**：`test/prompt-anchor-test.mjs:74-82` 的 `prefixOf()` 以【记忆】为前缀起点；`test/test-prompt.mjs:119-122` 断言了完整段落顺序。
- 结论：能用 A2-② 就不要动位置。

**A4　锚点追加预算放宽**
- 文件：`src/config.js:275-278`、`src/prompt.js:677`
- 改法：`maxExtraRead` 默认 `5` → `15`；或新增 `maxExtraReadTokens` 改用 token 预算。
- 测试：`test/prompt-anchor-test.mjs:34` 手工设了 `2`，不受默认值影响。

**A5　系统提示稳定性**（低优先）
- 位置：`src/prompt.js:258`（参与度按会话人设改写系统提示）、`src/orchestrator.js:819-821`（owner-identity 的 `extraSections` 插进系统提示）
- 影响：owner 说话/不说话两种情况系统提示不同 → **整条前缀（含系统提示）全部失效**。
- 改法：把 `ownerRules` 从系统提示挪到用户提示的易变区（【未读信息】附近）。

**A6　显式 cache_control**（可选）
- 文件：`src/llm.js:300-315`（`buildBaseBody` 无 `cache_control`）
- 仅对"需要显式断点"的网关有意义（Anthropic 类）；需按渠道能力分支，风险中。

### 验收标准
- 新增单测（补 `prompt-anchor-test.mjs`）：连续两轮构建 `buildUserPrompt`，中间**写入一条新记忆 + 发一次表情**，断言两轮"记忆+已读信息"前缀**逐字节一致**。当前必然失败 → 修复后通过。这就是本次问题的核心回归。
- 用量页观察 `cachedTokens / promptTokens`（`llm.js:624-628`）抬升。

## 二、问题③：群聊连贯性（"顺着你的话却不回"）

### 改动清单

**B1　结构化捕获"回复我"**（地基，先做）
- 文件：`src/app.js:842-851`（`ingestMessage` 里 `segmentsToText` 调用）、`src/store.js:83-110`（entry schema）、`src/store.js:14`（注释）
- 现状：`resolveReply`（`app.js:806-822`）已能拿到被引用者的 `senderId`，但结果只在 `segmentsToText` 里被渲染成文本，**没有落成字段**。
- 改法（最小侵入）：在 `app.js` 里用闭包变量接住 ——
  ```js
  let replyToSelf = false;
  resolveReply: async (mid) => {
    const info = await resolveReply(mid);
    if (info && selfIdNow && String(info.senderId) === String(selfIdNow)) replyToSelf = true;
    return info;
  }
  ```
  然后把 `replyToSelf` 传进 `store.appendIncoming`，entry 新增该字段。老存档无字段 = `null`，回落文本匹配。
- 兜底：文本含 `[引用 <selfNickname|botName>(QQ:<selfId>)：`（渲染格式见 `onebot.js:465-472`）。

**B2　"回复我"= 触发**（核心）
- 文件：`src/prompt.js:446-512`（`resolveContextTier`）
- 改法：新增 `replyToMe` 判定，与 `atMe` 同级（放在 `498-500` 旁）：命中即 `tier 1 / shouldRespond: true`。
- 语义变化：**1 档也会因"回复我"触发**（原本只认被 @/拍一拍）。
- 配套：加开关 `store.replyTriggers`（默认 `true`）；系统提示与设置页文案同步一句，避免用户困惑"我只设了仅艾特怎么还回"。

**B3　连贯窗口：机器人发完言后 N 秒必响应**
- 文件：`src/orchestrator.js`（新增 `Map lastSelfSpeakAt`；`onIncoming` `178-202`）；发言落点 `src/sender.js:174/262/328/368/385`（或统一挂到 `store.appendSelf`）
- 改法：机器人每次发言记录 `lastSelfSpeakAt[chatKey] = Date.now()`；`onIncoming` 里先判 `if (now - lastSelfSpeakAt < windowMs) → 视作触发`。
- 参数：`windowMs` 建议 60~120s，配置项 `store.continuityWindowMs`（`0` = 关闭）；加"窗口内响应次数上限"防刷屏。
- 与 `chatActive` 的区别：这是**自动短窗口**，不依赖模型 `finish` 带 topic；`chatActive`（`config.js:237-240`，默认关）是"长窗口 + 模型自主结束"。两者可并存。

**B4　3 档概率偏置**
- 文件：`src/prompt.js:482-508`
- 改法：`randomHit` 改为 `rollValue < effectivePercent`，其中
  `effectivePercent = replyToMe || 紧跟机器人发言 || (最近一条已读是我 && 本条含问号) ? Math.max(randomPercent, 60) : randomPercent`
- 约束：保持 `roll` 值语义不变（`482`、`orchestrator.js:511-512` 的"固定骰子"机制不动），只在**阈值端**做偏置。

**B5　（可选、风险最高）未触发不立即判死**
- 文件：`src/orchestrator.js:191-201`
- 现状：不触发**当场** `markEntryRead`，消息沉历史、不再补判 → 话题直接断。
- 改法：给 8~10s 的"待定"态，期间若又来一条相关消息（同作者 / 含问号 / 引用同一对象）→ 合并重判。
- ⚠️ 与 `onIncoming` 的"一次定生死"设计正面冲突（见 `orchestrator.js:150-165` 注释），会牵动 wake 语义与 `test/wake-semantics-test.mjs`。**建议最后做或先不做**，B1~B4 已能覆盖绝大部分体感。

### 验收标准
- 单测：`resolveContextTier` 传入 `replyToSelf: true` 的 entry，1/2/3 档均 `shouldRespond === true`。
- 单测：连贯窗口内 `onIncoming` 必触发；窗口外随机档行为回归原样。
- 现有 `test/wake-semantics-test.mjs` 必须全绿（B5 若做，需同步）。

## 三、问题②：思考链存储 —— 方案评估（回应你的四个想法）

| 你的想法 | 评估 |
|---|---|
| 新增模块存思考链，但 token 会飙升 | **成立**。整条注入 = 每轮固定多付一份**全价** token，且它是"新字节"，会打断前缀缓存 → 等于双份成本 |
| 限制注入数量 | **治标**。数量封顶只控上限，解决不了"该带哪几条"；带错比不带更糟（模型会被自己的陈旧推理锚定） |
| 反向溯源：AI 自行判断用哪次会话的思考链再调用 | **方向对**，也贴合本项目"工具即接口"哲学。但前提是模型得先知道"有哪些可选" → 需要一份**极轻量索引**（每条 = 时间 + 一句话结论，不注入正文）+ `recall_thought(id)` 工具按需拉取。成本：索引十几行，正文零成本按需付费。风险：模型未必意识到"我忘了东西" → 需在系统提示加一句元指令 |
| "把每次沉默后新开对话、不在原 session 新开" | **这条其实是最优解**（若我理解无误）：以**沉默为会话切分边界** —— 连续聊天时不重开会话、在**同一个 messages 数组上追加**，沉默超阈值才关闭重开。这样：① 思考链天然留在上下文，不用另建模块、不用重新注入；② 因为是"追加"，前缀缓存几乎全命中 → **增量成本只有新消息**，可能比现在"每轮重发 80 条已读信息"更便宜；③ 沉默即重置 → 输入不会无限膨胀，正好卡住你担心的 token |

### 落点评估（"沉默为界"其实不难）
`session.messages` **已经**持久化了完整的 OpenAI 序列（含 `tool_calls` / `tool` 结果：`sessions.js:281`、`orchestrator.js:1030-1031`），现在是"跑完即弃"，改成"同会话续用 + 沉默失效"即可。
代价：与"无状态、单次成本恒定"的架构承诺冲突（README 技术架构第 3 条）；且【已读信息】注入要改成"只注入增量"，否则重复。属大改，但收益最大。

### 建议：三层，互不互斥
1. **短期层（活跃对话内）**：沉默为界 + 同会话追加 → 思考链天然保留，成本靠前缀缓存压住。← **优先做这个**
2. **中期层（跨沉默）**：只把**蒸馏后的私有状态**（海龟汤答案 / 规则 / 待办）写进"自身记忆"，随提示词注入（体积小、可控）；**不注入完整 CoT**。
3. **长期层（历史 CoT）**：**零注入 + 索引 + `recall_thought` 工具**反向溯源，按需付费。

一句话：默认不花这份钱，需要时才花，且花的是小钱。

> 实现提示：第 2 层需要先补"自身记忆"出口 —— 现在记忆工具 `category` 只允许 `memberImpression`（`tools.js:652-672`、`memory.js:222-229`），且旧 `activeTopic/pendingThought` 被显式删除（`memory.js:124`）。需新增 category + 落 `_self.json` + 提示词单独段（放易变区）。

## 三·补充：短期层（会话延续）的落地设计

### 核心机制（确认可行）

```
群里两条消息的间隔 < T  →  继续同一会话（在 messages 数组上「追加」）
群里沉默 ≥ T            →  关闭当前会话 → 蒸馏私有状态 → 下次触发时带着蒸馏开新会话
```

**关键理由（用户提出，成立）**：沉默之后，前缀缓存的 TTL 早就过期了 —— 反正这一发要按全价算，那就"全价得少一点"：用一份**极短的蒸馏结果**代替几十条已读信息 + 整段 CoT 重放。从沉默后的第二发起，新会话又是纯追加，缓存重新命中。

**一个更精确的口径建议**：把沉默阈值 T 对齐各家的**缓存 TTL**（分钟级到小时级不等）。超过 TTL 意味着"继续长上下文"要全价重算 → 此时"关会话 + 蒸馏 + 重开"严格优于"硬撑"。所以 **T ≈ 缓存 TTL + 一点余量**，这不是拍脑袋的经验值。

### 六个前置条件（不满足就会翻车）

1. **依赖问题①的前缀稳定化**。延续的成本优势完全建立在"前缀字节不变"上；只要系统提示/表情包/记忆在会话中途抖一次，整条长上下文按全价重算，长会话成本会**线性爆炸**。**① 必须先做**。
2. **只追加增量，不能再注【已读信息】**。延续模式下 `buildUserPrompt` 需要一条"continuation 分支"：只带上次之后的新消息；否则 80 条窗口 + 全量 messages 双重计费。
3. **硬上限**：会话内轮次 / token 上限（如 30 轮 / 60k tokens），超了走"软重置"（关会话→蒸馏→重开）。沉默阈值管的是"外部静默"，管不了"连续聊 3 小时"。
4. **历史媒体要瘦身**。`messages` 里的 `image_url` 部分（看图工具注入的）如果每轮重发，图片 token 会持续膨胀且缓存收益差 —— 建议延续时把历史图片替换为文字占位（如 `[已看过这张图：<摘要>]`）。
5. **沉默口径按"该会话有没有新消息"算**，不是按"机器人多久没说话"。群里一直在聊但 3 档没触发到机器人，此时仍应延续（增量为那段已读），连贯性才有意义。
6. **跨进程重启要能续**。需要一个**持久化的"活动会话缓冲"**（`data/` 下落盘），不能只靠内存态 `Map`（现有 `activeTopics` 就是纯内存，重启即丢）。

### 蒸馏的时机

**在"关会话"那一刻做**——这是整条链路里唯一真正握有完整 CoT 的时刻（`session.messages` 里）。一次性的额外小调用，输出"私有状态"（海龟汤答案 / 已生效的规则 / 未完成待办），而不是摘要整段对话。成本一次性、可控。

### 需要承认的代价

架构承诺从「**无状态、单次成本恒定**」变成「**有界增长、单价靠缓存压住**」。这是刻意的取舍 —— 换来的是思考链连续性与真实的多轮推理能力（海龟汤、游戏、长任务、赌约这类场景从"完全不可用"变成"可用"）。
