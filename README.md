# QQ Agent

QQ Agent 是面向 QQ 会话的本地 AI 助手项目，提供模型调用、会话响应、记忆、人设、联网搜索及插件与技能扩展等能力。本仓库同时保留 **0.4 原项目**与 **0.5 架构重写版（未完成）**。

**0.5 涉及内核组织方式、组件组合与扩展接口的调整，因此单独放在 `0.5(unfinished)/` 中开发和验收；原项目代码保留在 `0.4/`，作为既有使用方式、扩展适配和功能迁移的参照。** 版本号更高，并不代表可以直接覆盖旧目录、复用全部数据，或已经通过所有旧功能的等价验收。

## 两个版本如何区分

| 方面 | 0.4 | 0.5 |
| --- | --- | --- |
| 版本定位 | 原项目的代码与既有功能基线 | 当前架构重写与后续开发的实现 |
| 架构基础 | 已有的应用结构，以及插件、技能和能力扩展机制 | 薄内核、明确的默认组件，以及可追加组合的实现层 |
| 扩展开发 | 使用 0.4 的加载方式和接口约定 | 使用 0.5 的 SDK、权限和生命周期约定；旧扩展需要逐项核对 |
| 功能判断依据 | 0.4 自身的源码与文档 | 0.5 的实现、功能对照和实际验收记录 |
| 使用入口 | [0.4 使用说明](./0.4/README.md) | [0.5 使用说明](./0.5%28unfinished%29/README.md) |

## 多账号（两个版本都已支持）

0.4 与 0.5 都提供了「账号中心」：同一个 QQ Agent 进程内管理多个 QQ 号，
每个号有独立的数据目录、控制台端口、模型/搜索 Key、白名单、记忆、存档、用量、
技能与插件开关/配置和日志；技能/插件代码全机器共用。

- 0.4：[多账号说明](./0.4/doc/extend_development/multi-account.md)（桌面端与 `npm run server` 共用）
- 0.5：[多账号说明](./0.5%28unfinished%29/docs/multi-account.md)（`npm run desktop` / `npm run server:accounts`；原单号入口保留）

每个 QQ 号仍需自己的 OneBot 端口；账号中心会检测重复地址/端口并提示。

## 为什么没有直接用 0.5 覆盖 0.4

### 1. 这次调整跨越了普通更新的兼容边界

普通更新通常延续原有程序结构和接口，用户可以在相对明确的升级路径上获得修复或新功能。0.5 改动的范围更深：应用如何启动、组件如何装配、扩展如何获取能力，以及资源如何在停止或失败时释放，都需要按新的契约组织。

例如，0.5 原生插件通过 `setup(ctx)` 注册能力；工具处理函数、日志接口和发送消息的入口，也需要遵循当前 SDK。旧扩展中可调用的日志函数、`execute(ctx, args)` 参数顺序，或直接访问旧发送器的写法，不能仅靠移动文件就假定继续有效。**即使两个版本的扩展都写着 `apiVersion: 1`，也不能据此认定接口兼容。**

单独标出版本，可以让使用者在安装、开发扩展和排查问题之前，就知道自己面对哪一套约定，而不是覆盖更新后才发现行为变化。具体差异见 [0.4 扩展能力对照与迁移说明](./0.5%28unfinished%29/docs/v04-extension-parity.md)。

### 2. 保留现有用户可理解、可核对的代码基线

已经围绕 0.4 配置模型、编写插件或形成使用习惯的用户，需要能够继续查到与原程序对应的源码和说明。直接覆盖仓库首页下的全部实现，会让旧教程、旧扩展和新代码混在一起，增加判断问题来源的成本。

保留独立的 `0.4/`，可以按文件和行为对照旧实现，判断某个差异是有意调整、尚未迁移，还是新版本的回归。遇到问题时，也有明确的旧版源码可供恢复和复现。

这里保留的是原项目基线，不代表承诺两个版本永久同步开发，也不代表为 0.4 另行承诺长期维护周期。

### 3. 功能迁移需要验证实际行为，不能只对照名称

同样叫“记忆”“人设”或“插件”的功能，在默认值、状态保存、异常处理、并发和退出清理上，仍可能存在差异。页面上出现了相同选项，或者某个单元测试通过，都不足以证明旧版本的整条使用流程已经完整保留。

0.5 的迁移思路是逐项比较实际能力：保留已有的合适实现，补齐确实缺失的行为，并对有意改变或尚待验收的部分作出说明。迁移时也要沿用 0.5 的组件与扩展边界，避免为了补一个功能，把旧版内部结构整块搬回来。

两个目录并存，让“架构已重写”和“功能已验证”成为可以分别检查的事实。迁移原则见 [0.4 到 0.5 功能对照计划](./0.5%28unfinished%29/docs/v04-parity-plan.md)。

### 4. 新架构仍需独立完成运行与验收

源码、接口文档和自检工具已经存在，并不等于真实 QQ 环境中的启动、收发消息、数据隔离、扩展执行和发布流程都已验证完成。0.5 当前仍有开发与验收边界，不能仅凭版本号就宣布它全面替代了 0.4。

因此，仓库把原项目和重写版分开呈现，方便使用者按自己的需求评估。0.5 的具体完成情况与限制，应以其 [README](./0.5%28unfinished%29/README.md) 和 [进度记录](./0.5%28unfinished%29/progress.md) 为准。

## 0.5 希望改进什么

0.4 本身已经支持插件、技能和能力扩展。0.5 在此基础上，进一步把应用内部的职责和替换边界明确下来：

- **让默认实现可以组合和替换。** 前端面板、后端服务与核心业务都有明确的默认组件；可信的组合层可以替换或包装指定组件，减少新需求对其他模块的牵连。
- **让扩展依赖明确的接口。** 普通插件和技能通过 SDK 获取能力，配置、权限、工具注册与生命周期都有对应约定，便于开发、测试和定位不兼容问题。
- **让资源管理更可控。** 组件或扩展注册的资源需要随停止、启动失败等情况清理，减少重复加载后遗留监听器或后台任务的问题。
- **让人工和 AI 辅助开发都有可核对的依据。** 提供开发文档、示例、能力对照和自检工具，帮助新增功能遵循当前接口；实际加载、配置、执行和发布仍要分别验证。

其中，普通插件、技能与可信的架构替换层具有不同的权限边界。安装社区扩展不等于允许它自动接管整个应用内核。设计细节见 [0.5 默认实现与追加式组合说明](./0.5%28unfinished%29/docs/architecture-composition.md)。

## 应该选择哪个版本，如何迁移

如果已有围绕 0.4 的部署或扩展，先保留原有环境，再核对 0.5 是否覆盖自己的必需功能，以及相关流程是否完成验收。如果希望参与新架构开发、适配扩展或测试新实现，可以从 `0.5(unfinished)/` 开始，并先阅读该版本说明。

尝试迁移时：

1. **先备份旧版配置和数据。** 保留能够恢复原环境的副本。
2. **为两个版本分别准备运行目录和数据目录。** 不要让它们同时读写同一份真实运行数据。
3. **按 0.5 的说明重新核对配置与扩展。** 不要假定复制整个旧数据目录、插件目录或依赖目录就完成了迁移；兼容适配器的存在也不代表所有旧接口都受支持。
4. **先在独立环境验证关键流程。** 确认所需的消息收发、记忆、人设和扩展行为，再决定是否替换自己的日常使用环境。

## 协议端与第三方许可

QQ Agent 通过 OneBot v11 连接用户自行安装、配置和运行的协议端。本项目负责模型调用、会话处理、记忆、人设及扩展等应用层能力。本文采用手动准备外部协议端的接入方式，不需要运行自动安装脚本；协议端和 QQ 客户端的安装与运行由用户管理。

请先按所选协议端的说明完成安装与登录，再在对应版本的 OneBot 设置中填写 WebSocket 地址、HTTP API 地址与访问令牌。不同实现对扩展接口的支持可能不同，应按实际需要验证，不能仅凭 OneBot v11 名称假定所有功能兼容。

0.4 的“仿真群友”思路与初始实现来自 [Derpyu520/qq-bridge](https://github.com/Derpyu520/qq-bridge)。本项目以 [MIT 许可](./LICENSE) 发布；第三方依赖及 QQ 客户端仍适用各自的许可与使用条款，本项目的许可不构成对它们的重新授权。
